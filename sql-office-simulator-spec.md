> **Status:** v1.1. Product decisions are confirmed (Section 2).

## 1. Product Overview

**SQL Office Simulator** is a free, learn-by-doing web platform where learners practice SQL by working inside a simulated company. Instead of abstract exercises, learners receive realistic business requests ("The VP of Sales wants last quarter's top 10 customers by revenue") and answer them by writing SQL against a real database.

- Learners **sign up / log in**, **pick an industry domain**, and progress through **5 levels**.
- Each level simulates a bigger, more complex company with more tables, more data, and harder questions.
- Each level has **100 questions**. Total: 7 domains × 5 levels × 100 = **3,500 questions**.
- Learners write and test queries in a built-in SQL editor against a provided database.
- The platform asks learners to be honest and **not rely on AI**. This is a stated policy, not something the platform enforces (Section 8).
- Progress, XP, streaks, and level-ups are tracked per learner, per domain.

### Core principle
Every question is framed as a **business request from a named stakeholder** with context, not as a textbook exercise.

## 3. Goals and Non-Goals

### Goals
1. Make learners feel like they work in a real office answering real leadership questions.
2. Provide progressive difficulty across 5 levels and 7 domains.
3. Grade answers automatically and fairly (correct result set, not identical SQL text).
4. Track progress and motivate with XP, levels, streaks, and badges.
5. Set a clear honesty expectation around AI use.

### Non-Goals
- Detecting, monitoring, or blocking cheating or AI use.
- Certificates, payments, subscriptions.
- Live mentoring, video lessons, or community forums.
- Non-SQL languages.
- Native mobile apps (responsive web only).

## 4. Users and Core Flows

**Primary user:** SQL learner (student, career-switcher, analyst).
**Secondary user:** Admin (manages content and config).

### Learner flow
1. Land on home page → sign up / log in (accept the honor pledge at signup).
2. Choose a **domain**.
3. Domain dashboard shows Levels 1–5 (only Level 1 unlocked initially) and overall progress.
4. Enter a level → **office view**: company profile, team directory, data dictionary, ER diagram, and an inbox of questions.
5. Open a question → read the request → write SQL → **Run** (preview) → **Submit** (graded).
6. Earn XP, get feedback, move on.
7. After meeting the unlock criteria, the next level unlocks with a level-up screen.
8. Learners can switch domains any time. Progress is stored per domain.

## 7. Question Design and AI Generation

### 7.1 Question object

```json
{
  "id": "ecom-L2-045",
  "domain": "ecommerce",
  "level": 2,
  "order": 45,
  "difficulty": "core",
  "title": "Repeat buyers by region",
  "stakeholder": { "name": "Priya Nair", "role": "Head of Marketing" },
  "request": "We're planning a loyalty campaign. Which regions have the highest share of customers who ordered more than once in 2025?",
  "context_notes": "Use delivered orders only. Ignore cancelled orders.",
  "concepts": ["JOIN", "GROUP BY", "HAVING", "subquery"],
  "expected_columns": ["region", "repeat_buyer_pct"],
  "reference_sql": "SELECT ...",
  "validation": {
    "order_sensitive": true,
    "column_names_sensitive": false,
    "numeric_tolerance": 0.01
  },
  "hints": ["Start by counting orders per customer.", "Filter status first.", "..."],
  "solution_explanation": "Markdown explanation shown after solving or after N failed attempts.",
  "xp": 20,
  "estimated_minutes": 8
}
```

### 7.2 Writing rules (given to the AI generator as a prompt spec)
- Written as a **realistic workplace message** from a named role (CEO, Ops Manager, Finance Analyst, etc.).
- Include business context and explicit assumptions (e.g., "exclude test accounts", "use calendar quarters"). Every rule that affects the answer must be stated so grading is deterministic.
- **Level 1 covers all departments** of the domain, since the learner is the only data person.
- Each question maps to concept tags matching the level's concept matrix (Section 6).
- No question answerable by trivial `SELECT *` inspection.
- No duplicate or near-duplicate questions within a domain-level.

### 7.3 AI generation pipeline (automated, since there is no manual review)
Because 3,500 questions cannot be reviewed by hand, correctness relies on **automated gates**:

1. **Blueprint:** for each domain-level, generate a coverage matrix that assigns concepts and difficulty to each of the 100 slots.
2. **Generate:** for each slot, the AI writes the question JSON, including `reference_sql`, hints, and explanation, using the real schema metadata as context.
3. **Execute check:** run `reference_sql` on the level dataset. Must run without error within the time limit, return the expected columns, and return a sensible row count (non-empty unless flagged, and not the entire table by accident).
4. **Concept check:** parse the SQL (AST) and confirm it actually uses the tagged concepts (e.g., a "window function" question must contain a window function).
5. **Independent solver check:** a *second, separate* AI pass sees only the question text and schema (not the reference SQL) and writes its own SQL. If its result set matches the reference, the question is considered unambiguous. If not, regenerate or rewrite the question.
6. **Duplicate check:** embedding or text similarity to reject near-duplicates.
7. **Difficulty sanity check:** the solver's number of attempts/complexity is used to confirm the difficulty label fits the slot.
8. **Store** passing questions in `/content/{domain}/{level}/` and log failures for regeneration (retry up to N times, then queue for later).

### 7.4 Learner-reported issues (quality feedback loop)
Each question has a **"Report a problem with this question"** button (wrong answer, unclear wording, data issue). Reports are stored and shown in the admin panel with a count per question. Questions above a report threshold are auto-hidden and queued for regeneration. This is the primary correction mechanism after launch.

### 7.5 Content CI
On every content change, run the checks in 7.3 steps 3–6 and fail the build on errors. IDs must be unique and numbered 1–100 per domain-level.

## 8. Honor Policy (No Enforcement)

Cheating cannot be prevented or verified on the web, so the platform does **not** try. It sets expectations clearly and kindly:

- **Honor pledge at signup** and a short reminder at the start of each level. Suggested copy:
  > "This simulator works only if you do the work yourself. Please don't use AI tools or copy solutions. You're here to build real skills, and the only person you'd be fooling is you. Be honest, and enjoy the learning."
- A one-line reminder in the question workspace footer: *"Solve it yourself. That's where the learning happens."*
- Learners must tick "I will not rely on AI to solve questions" at signup (stored as a boolean with a timestamp).
- **Not included:** paste blocking, keystroke or tab-switch tracking, similarity detection, proctoring, per-learner randomized data, or integrity scoring.

### Retained for security and grading (not anti-cheat)
- **Submit rate limiting** (e.g., 1 per 5 seconds) to protect the sandbox from abuse.
- **Hidden validation dataset:** each dataset has a second variant with different generated values. A submission must match the reference on both. This is a *grading correctness* measure so a query like `SELECT 42` doesn't pass; it isn't cheating detection.
- **No answer leakage:** reference SQL and expected rows are never sent to the client.

## 9. Functional Requirements

### 9.1 Authentication and Accounts
- Sign up, log in, log out, password reset, email verification, Google OAuth.
- Profile: display name, avatar, timezone.
- Roles: `learner`, `admin`.

### 9.2 Domain and Level Selection
- Domain picker with a card per domain (icon, short description, learner progress).
- Domain dashboard: five level cards with locked / unlocked / completed states and % progress.

### 9.3 Office Simulation Experience
- **Company profile:** name, size, story ("You've just joined as the first data hire at...").
- **Team directory / org chart** of the stakeholders who send questions.
- **Data dictionary:** tables, columns, types, descriptions, relationships.
- **ER diagram** auto-generated from schema metadata.
- **Inbox-style question list** with status (new / attempted / solved), stakeholder avatar, priority tag, and difficulty.
- Narrative touches: level intro message and a "promotion" message on level-up.

### 9.4 Question Workspace
Desktop layout: left = request, context, schema reference; right = SQL editor and results.
- **SQL editor:** Monaco with syntax highlighting, line numbers, Ctrl/Cmd+Enter to run. Autocomplete limited to the current schema's table and column names.
- **Run:** executes the query and shows the first 100 rows, column names, and execution time. Does not count as an attempt.
- **Submit:** validates, records an attempt, and gives feedback.
- **Friendly SQL error messages.**
- **Schema explorer** with sample rows.
- **Hints:** progressive, up to 3 per question. Each hint used reduces XP by 25%.
- **Solution:** available after 3 failed submissions or after solving. Viewing a solution before solving gives 0 XP for that question.
- **Scratchpad notes** and **query history** per question.
- **Report a problem** button (7.4).

### 9.5 Answer Validation
- Execute the learner's query and compare **result sets** to the reference:
  - Order-insensitive unless the question asks for ordering.
  - Column count and order must match; names optionally ignored.
  - Numeric tolerance for rounding.
  - Must also match on the hidden validation dataset.
- Failure feedback never reveals expected rows. Use generic hints: row-count mismatch, column mismatch, "some values differ".
- Only a single `SELECT` / `WITH ... SELECT` statement is allowed.

### 9.6 Progress and Gamification
- **XP** by difficulty (warm-up 10, core 20, challenging 35, boss 60), reduced by hints and repeated failures.
- **Rank titles:** Intern → Analyst → Senior Analyst → Data Lead → Head of Data.
- **Level-up** screen when unlock criteria are met.
- **Streaks:** consecutive days with at least one solved question.
- **Badges:** first query, 10 in a row, no-hints level, domain master, all five levels in a domain, all seven domains.
- **Progress page:** completion per domain and level, concept-mastery radar, accuracy, time spent, recent activity.
- **Weak-area suggestions** based on concept tags with the highest failure rates.

### 9.7 Admin Panel (minimal)
- Browse and preview questions, view validation status, see reported-problem counts, trigger regeneration.
- Manage dataset versions.
- View learner progress (aggregate).
- Edit config: unlock thresholds, hint penalty, attempts before solution, rate limits.

## 10. Technical Architecture

### 10.1 Stack [DEFAULT]
- **Frontend:** Next.js (App Router), TypeScript, Tailwind CSS, shadcn/ui; Monaco Editor; a diagram library for ER diagrams.
- **Backend:** Next.js API routes / server actions (sandbox in a separate service if isolation is needed).
- **App DB:** PostgreSQL via Prisma (users, progress, attempts, content metadata).
- **Practice DB cluster:** a **separate** PostgreSQL instance for sandboxes. Never share it with the app DB.
- **Auth:** Auth.js or a managed provider.
- **Jobs:** queue/cron for dataset generation and question-generation pipeline runs.

### 10.2 Practice Databases
- One database (or schema) per domain per level, e.g. `ecom_l1` ... `saas_l5`: **35 datasets**, each with a **hidden validation variant** (different seed).
- Datasets are **generated by seeded scripts** (Python/Faker or SQL generators) with realistic distributions and referential integrity. Messiness (NULLs, duplicates, inconsistent casing) increases at Levels 4–5.
- Schema metadata (descriptions, relationships) is stored as JSON for the data dictionary and ER diagrams.
- Because there is a single shared dataset per level (no per-learner variants), datasets can be pre-built and read-only.

### 10.3 SQL Sandbox Security (critical)
- **Read-only DB role**, `SELECT` only. No DDL/DML. Block file, network, and admin functions (`COPY`, `pg_read_file`, `dblink`, etc.).
- `statement_timeout` (5 s for L1–L2, up to 15 s for L4–L5), idle timeouts, per-user connection limits.
- Preview limited to 1,000 rows; full comparison happens server-side.
- Execute inside a transaction that is always rolled back; `default_transaction_read_only = on`.
- Parse SQL (e.g., `pgsql-parser`) and **reject anything other than one `SELECT`/`WITH` statement**.
- `search_path` limited to the assigned dataset schema.
- Sandbox pool isolated from app infrastructure with least-privilege credentials.
- Log every executed query with user id, question id, duration, and outcome.

**Add one dark neutral for text**, since all four brand colors are light: `--ink: #1F3550` (headings, body text, editor chrome). A lighter tint of `--mist` (e.g. `#EAF6F9`) is fine for large surface backgrounds. Keep `--ink` and white as the only text colors.

### 11.2 Accessibility rules for this palette
- **Never place white text on `--ocean`, `--sky`, or `--mist`.** Contrast is too low. Use `--ink` text on all palette colors.
- Primary buttons: `--ocean` background with `--ink` text, and a 2px `--ink` border or a darker `--ocean` shade (e.g. `#5F8DB8`) on hover for clear affordance.
- Do not rely on color alone for state (locked / solved / error). Pair with icons and labels.
- Error and success states may use standard red and green tones (adjusted for AA contrast) since the palette has no semantic colors.
- Target WCAG AA on all text and interactive elements. Verify with a contrast checker.

## 12. Non-Functional Requirements

- **Performance:** query run < 2 s for typical L1–L3 queries; page loads < 2 s.
- **Scalability:** sandbox pool sized for concurrent learners; queue or throttle on overload.
- **Security:** OWASP Top 10, hashed passwords (argon2/bcrypt), CSRF protection, strict input validation, rate limiting, secrets in environment variables.
- **Privacy:** minimal PII, support for account deletion.
- **Reliability:** app DB backups; sandbox datasets are rebuildable from generator scripts.
- **Observability:** structured logs, error tracking, sandbox query metrics.
- **Testing:** unit tests (validation), integration tests (sandbox security), e2e tests (learner flow), content CI.
- **Cost awareness:** the product is free, so keep hosting costs low: pre-built read-only datasets, connection pooling, and query timeouts.
